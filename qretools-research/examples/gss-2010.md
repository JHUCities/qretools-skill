# Example: GSS 2010, real answers and synthetic answers

This example uses the workspace
[JHUCities/qretools-gss](https://github.com/JHUCities/qretools-gss) and its instrument
`gss_2010`, in the release `v15`. It makes two datasets of one instrument:

- a dataset of the real answers of 2010, from the data of NORC's General Social Survey
  (GSS);
- a dataset of synthetic answers, from a run of qretools-harness.

Then it checks the two datasets and compares their CSV views. The two datasets use the
same DDI, so each value has the same variable URN in the two views.

The authority is the README of qretools-gss, section "Maps and datasets".

**Caution: do not commit or publish the GSS data. Its licence does not permit
publication. This rule applies to the data file, the CSV file that `tools/columns.py`
writes, a dataset and a CSV view. Do not write a figure from the data in a commit or a
pull request. Do not write it in a published report or in this repository.**

## The names in this example

| Name | What it is |
|---|---|
| `<ddi>` | The DDI URL of the instrument: `https://jhucities.github.io/qretools-gss/v15/instruments/gss_2010.json`. |
| `<version>` | qretools 2.0.0-alpha.13 or later. An earlier version cannot read a DDI URL. |
| `<work>` | A folder outside the clone, for the data. For example `~/gss-work`. |

Give `<ddi>` to each command that reads the DDI. Then each dataset records where its DDI
came from.

## Prepare the work

1. Clone the workspace at the release:
   `git clone --branch v15 https://github.com/JHUCities/qretools-gss`.
2. Make the folder `<work>`.
3. Download the DDI into it: `curl -fsSL -o <work>/gss_2010.json <ddi>`.
4. Download NORC's cumulative data in SPSS format:
   [GSS_spss.zip](https://gss.norc.org/Documents/spss/GSS_spss.zip).
5. Unzip it into `<work>`.
6. Find `gss7224_r3a.sav` in `<work>`.

   If the zip holds a different `.sav` file, stop. Tell the researcher.
7. In the clone, make a Python environment: `python3 -m venv .venv`.
8. Install pyreadstat in it: `.venv/bin/pip install pyreadstat`.

The GSS map was made from release 3a, `gss7224_r3a.sav`. The link gives the newest
release. NORC's [SPSS page](https://gss.norc.org/get-the-data/spss.html) names that release.
The map cites its release, so a newer release needs a change to the workspace first.

## Make the CSV of 2010

Run each command in the clone.

1. Run `.venv/bin/python -I tools/columns.py <work>/gss7224_r3a.sav <work>/gss_2010.json 2010 -o <work>`.
2. Read the lines that `tools/columns.py` writes. Each line names a variable or a code,
   never a value.
3. Run `git status`.
4. Make sure that `maps/gss_2010-ddi-gss.columns.json` did not change.

   If it changed, stop. Tell the researcher. Do not commit the change without a pull
   request that the researcher accepts.

`tools/columns.py` writes `<work>/gss_2010-2010.csv`. It holds the rows of 2010. It also
writes the map again. With the same DDI and the same data file, the map does not change.

## Make the GSS dataset

1. Run this command in the clone:

   ```sh
   npx -y qretools@<version> responses <work>/gss_2010-2010.csv \
     --map maps/gss_2010-ddi-gss.columns.json \
     --ddi <ddi> -o <work>/gss2010.json
   ```

2. Read the findings on stderr. Findings about `filtered` and `censored` columns are
   normal. The README of the workspace explains each of them.

The map gives who answered, the citation, the date and mode of each interview, and the
weights. The command needs no other option. If `tools/columns.py` writes a line about
MODE, a mode of that year has no term. Read the README of the workspace, section "What the
GSS map holds".

## Make the synthetic dataset

**Caution: put the run folder outside the clone. The folder must not exist, or it must be
empty.**

1. Copy `examples/gss_2010/config.toml` from the harness repository to
   `<work>/config.toml`. Its `instrument` is `<ddi>`.
2. Set the model, the seed and the prompts for the researcher's study.
3. Run `qretools-harness check-config <work>/config.toml`.
4. Start the model server.
5. Run `qretools-harness respond <work>/config.toml -n <respondents> -o <work>/run-1`.

The README in `examples/gss_2010/` of the harness gives more information about this run.

The harness writes `<work>/run-1/dataset.json`. The dataset says that the questions were
asked in a simulation, and that "synthetic" answered.

## Export the views

The workspace declares no access levels. Do not give `--access`.

1. Run `npx -y qretools@<version> dataset export <work>/gss2010.json --provenance --ddi <ddi> -o <work>/gss2010-provenance.json`.
2. Run `npx -y qretools@<version> dataset export <work>/run-1/dataset.json --provenance --ddi <ddi> -o <work>/run-1-provenance.json`.
3. Run `npx -y qretools@<version> dataset export <work>/gss2010.json --csv --ddi <ddi> -o <work>/gss2010.csv`.
4. Run `npx -y qretools@<version> dataset export <work>/run-1/dataset.json --csv --ddi <ddi> -o <work>/run-1.csv`.

If a command writes nothing and gives `dataset-ddi`, `responses` did not make that
dataset from this DDI. Stop. Tell the researcher.

## Check the datasets

Do these checks before you compare the views. If a check fails, stop. Tell the
researcher which check failed.

1. Run the `responses` command of "Make the GSS dataset" again. It must say
   `<work>/gss2010.json: unchanged`.
2. In each provenance view, find the `OtherMaterial` whose `TypeOfMaterial` is
   `instrument DDI`.
3. Make sure that the two `UserID` digests are the same.
4. In each provenance view, find the `SourceType` of the `DataSource`.
5. Make sure that the `StringValue` in the GSS provenance view is
   `ResearchData.Published`.
6. Make sure that the `StringValue` in the synthetic provenance view is `Other`, and
   that its `OtherValue` is `synthetic`. Steps 5 and 6 show that you did not exchange
   the two files.
7. In each provenance view, find the `DataCollectionDate` of the `CollectionEvent`.
8. Tell the researcher the two periods. The GSS answers are from 2010. The synthetic
   answers are from the day of the run.

A run makes its dataset one time. Do not make the synthetic dataset again to
check it. A new run gives new answers.

## Compare the two views

1. Load the two CSV views as data, in R or Python.
2. Keep the variable URNs that are in the two views.
3. For each URN, compare the values of the two views.
4. Do not join the views on `respondent`. The respondents are different.

Read these points before you report a difference:

- The GSS map marks some columns `filtered`, and some values `censored` (top codes and
  bottom codes). The GSS dataset has no value there. The synthetic dataset can have one.
- The GSS CSV view also holds the metadata columns of the map, for example the mode and
  the weights. Their URNs are the URNs of the dataset, so the synthetic CSV view does not
  hold them.
- The GSS values are not weighted. Do not choose a weight. The provenance view of the
  GSS dataset holds NORC's advice about the weights, in its `Weighting`. Give the advice
  to the researcher. Ask the researcher which weight to use.
- The missing codes that the model can give are the `missing` list of the config. Tell
  the researcher which codes each dataset can hold.

## The shape of the result

A comparison of datasets of one instrument has this shape. The provenance of each
dataset gives each cell. This table holds no figure from the data.

| Dataset | How the questions were asked | Who answered | Weights |
|---|---|---|---|
| GSS 2010 | the terms that the map gives the codes of `MODE`, for example `Interview.Telephone` | `ResearchData.Published` | the weight columns of the map, with NORC's advice |
| Qualtrics test responses | `Simulation` | "generated by the survey platform" | none |
| A harness run | `Simulation` | "synthetic" | none |

This example makes the first and the last row. A Qualtrics dataset comes from the
Qualtrics export of a fielded survey and its Qualtrics map (see
[reference/workspace.md](../reference/workspace.md)).

## Share the result

You can publish the two provenance views. Before you publish a view, make sure that it
holds no `ItemSet`. An `ItemSet` holds answers. Publish the `LICENSE.md` of the workspace with
the GSS provenance view, because the view quotes the GSS codebook.

Do not publish the CSV views or the datasets. Do not publish a figure from the GSS data
yourself. The researcher decides what to publish.
