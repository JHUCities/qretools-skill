# Example: GSS 2010, real answers and synthetic answers

This example uses the workspace
[JHUCities/qretools-gss](https://github.com/JHUCities/qretools-gss) and its instrument
`gss_2010`. It makes two datasets of one instrument:

- a dataset of the answers in NORC's General Social Survey data for 2010;
- a synthetic dataset, from a language model, made with qretools-harness.

Then it compares the two CSV views. The two datasets use the same DDI file, so each
value has the same variable URN in the two views.

The authority is the README of qretools-gss, section "Maps and datasets".

**Warning: the GSS data is not licensed for publication. Do not commit or publish the
data file, the CSV that `tools/columns.py` writes, a dataset, or a CSV view. Do not
write a figure from the data in a commit, a pull request, a report that you publish, or
this repository.**

## Get ready

**Caution: do not make a shallow clone. `build` refuses it.**

1. Clone the workspace: `git clone https://github.com/JHUCities/qretools-gss`.
2. Read the qretools version in its `mise.toml`. Use that version as `<version>` in each
   command below.
3. Make a folder outside the clone for the data, for example `~/gss-work`. This example
   calls it `<work>`.
4. Download NORC's cumulative data in SPSS format:
   [GSS_spss.zip](https://gss.norc.org/Documents/spss/GSS_spss.zip).
5. Unzip it into `<work>`.
6. Find `gss7224_r3a.sav` in `<work>`.
7. If the zip holds a different `.sav` file, then stop. Tell the researcher.
8. In the clone, make a Python environment: `python3 -m venv .venv`.
9. Install pyreadstat in it: `.venv/bin/pip install pyreadstat`.

The GSS map was made from release 3a, `gss7224_r3a.sav`. The link serves the newest
release, and NORC's [GSS data page](https://gssdataexplorer.norc.org/gss_data) names it.
The map cites its release, so a newer release needs a change to the workspace first.

The `.gitignore` of the workspace ignores `.venv/`, `*.sav` and `dist/`. Do not depend on
it: keep the data in `<work>`.

## Build the DDI and the map

Run each command in the clone.

1. Run `npx -y qretools@<version> build . -o dist`.
2. Run `.venv/bin/python -I tools/columns.py <work>/<file>.sav dist/instruments/gss_2010.json 2010 -o <work>`.
3. Read the lines that the tool writes. Each line names a variable or a code, never a
   value.
4. Run `git status`.
5. If `maps/gss_2010-ddi-gss.columns.json` changed, tell the researcher. Do not commit
   the change without a pull request that the researcher accepts.

The tool writes `<work>/gss_2010-2010.csv`. It holds the rows of 2010.

## Make the GSS dataset

1. Run this command:

   ```sh
   npx -y qretools@<version> responses <work>/gss_2010-2010.csv \
     --map maps/gss_2010-ddi-gss.columns.json \
     --ddi dist/instruments/gss_2010.json -o <work>/gss2010.json
   ```

2. Read the findings on stderr. Notes about `filtered` and `censored` columns are
   expected: the README of the workspace explains each one.

The map gives who answered, the citation, the date and mode of each interview, and the
weights. The command needs no other option. If `tools/columns.py` writes a note on
MODE, a mode of the year has no term. Read the README of the workspace, section "What the
GSS map holds".

## Make the synthetic dataset

**Caution: put the run folder outside the clone. The folder must not exist, or it must be
empty.**

1. Copy `examples/config.toml` from the harness repository to `<work>/config.toml`.
   That example is for `gss_2010`.
2. Set `instrument` to the absolute path of `dist/instruments/gss_2010.json` in the
   clone. Use the same file as for the GSS dataset.
3. Set the model, the seed and the prompts for the researcher's study.
4. Run `qretools-harness check-config <work>/config.toml`.
5. Start the model server.
6. Run `qretools-harness respond <work>/config.toml -n <respondents> -o <work>/run-1`.

The harness writes `<work>/run-1/dataset.json`. The dataset says that "synthetic"
answered, in a simulation.

## Export the views

The workspace declares no access levels. Do not give `--access`.

1. Run `npx -y qretools@<version> dataset export <work>/gss2010.json --provenance --ddi dist/instruments/gss_2010.json -o <work>/gss2010-provenance.json`.
2. Run `npx -y qretools@<version> dataset export <work>/run-1/dataset.json --provenance --ddi dist/instruments/gss_2010.json -o <work>/run-1-provenance.json`.
3. Run `npx -y qretools@<version> dataset export <work>/gss2010.json --csv --ddi dist/instruments/gss_2010.json -o <work>/gss2010.csv`.
4. Run `npx -y qretools@<version> dataset export <work>/run-1/dataset.json --csv --ddi dist/instruments/gss_2010.json -o <work>/run-1.csv`.

If a command writes nothing and gives `dataset-ddi`, that dataset was not made from this
DDI. Stop, and tell the researcher.

## Compare the two views

1. In each provenance view, find the `OtherMaterial` whose `TypeOfMaterial` is
   `instrument DDI`. Make sure that the two `UserID` digests are the same.
2. Load the two CSV views as data, in R or Python.
3. Keep the variable URNs that are in the two views.
4. For each URN, compare the values of the two views.
5. Do not join the views on `respondent`. The respondents are different.

Read these points before you report a difference:

- The GSS map marks some columns `filtered`, and some values `censored` (top codes and
  bottom codes). The GSS dataset has no value there. The synthetic dataset can have one.
- The GSS view also holds the metadata columns of the map, for example the mode and the
  weights. Their URNs are the URNs of the dataset, so the synthetic view does not hold
  them.
- The GSS values are not weighted. Do not choose a weight. The provenance view of the
  GSS dataset holds NORC's advice about the weights, in its `Weighting`. Give the advice
  to the researcher, and ask which weight to use.
- The missing codes that the model can give are the `missing` list of the config. Tell
  the researcher which codes each dataset can hold.

## Share the result

You can publish the two provenance views. Publish the `LICENSE.md` of the workspace with
the GSS provenance view, because the view quotes the GSS codebook.

Do not publish the CSV views or the datasets. Do not publish a figure from the GSS data
yourself. The researcher decides what to publish.
